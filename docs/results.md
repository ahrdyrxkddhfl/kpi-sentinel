아래 수치는 최종 성능과 무관하며 비교 기준으로 사용하지 않는다.

| 지표 | 값 |
|---|---|
| Precision | 0.533 |
| Recall | 0.667 |
| F1 | 0.593 |
| TP / FP / FN | 16 / 14 / 8 |

조건: RTT 1종, 3일치 1분 간격, 스파이크 3회, window=60, z>3, point-wise 평가

이 단계에서 확인한 것:

- FP 14개는 계절성이 아니라 정규분포 3σ 꼬리에서 발생.
  대략적 기대값 11.7개(4320 × 0.0027)와 같은 수준.
- 스파이크 구간 내 z가 7.06에서 2.25까지 감쇠.
  이상값이 rolling window에 누적되며 표준편차를 부풀리는 자기오염.
- 계절성을 무시한 전역 z-score가 F1 1.000.
  가장 단순한 방법이 만점을 받는다는 것은 시뮬레이터 난이도가
  지나치게 낮았다는 뜻이므로, 시뮬레이터를 전면 교체함.

## 시뮬레이터 검증

KPI 7종 / 21일 / 1분 간격 / 이상 비율 4.12% / warmup 7일

> 아래 수치는 `scripts/validate_simulator.py`로 재현 가능.

### 시나리오별 최대 이탈폭

정상 구간의 표준편차를 단위로 하며, 각 KPI의 direction 기준으로
나쁜 방향의 최대 이탈폭을 이벤트별로 구해 평균한 값.

| 시나리오 | 라벨 | 이탈폭 |
|---|---|---|
| spike | 1 | 5.19 sd |
| config_change | 1 | 3.88 sd |
| node_down | 1 | 3.71 sd |
| gradual_degradation | 1 | 3.54 sd |
| traffic_surge | 0 | 2.25 sd |

초기 설정에서는 정상 시나리오인 traffic_surge가 2.95 sd로,
실제 장애인 spike(1.97 sd)와 gradual_degradation(2.84 sd)보다
크게 튀었다. 이 상태에서는 크기만으로 정상과 장애를 구분하는 것이
불가능하므로, 시나리오별 강도를 재조정해 정상 이벤트를 최하위로 내렸다.

### 부하 지표와 품질 지표의 분리

traffic_surge는 정상적인 트래픽 증가이므로, 부하 지표만 상승하고
품질 지표는 거의 변하지 않도록 설계했다.

| KPI | 구분 | traffic_surge | spike |
|---|---|---|---|
| link_util_pct | 부하 | 3.71 sd | 해당 없음 |
| prb_util_pct | 부하 | 3.64 sd | 해당 없음 |
| rtt_ms | 품질 | 0.70 sd | 5.84 sd |
| packet_loss_pct | 품질 | 0.95 sd | 5.44 sd |

spike의 부하 지표가 "해당 없음"인 것은 해당 시나리오의 affects에
포함되지 않아 주입 자체가 없기 때문이다.

### 설계 의도 (미검증)

위 이탈폭 차이를 탐지기가 실제로 활용할 수 있는지는 탐지 엔진을
구현한 뒤 측정한다. 현재 확인된 것은 데이터상 두 지표군이 분리되어
있다는 사실까지이며, 오탐 감소 여부는 아직 측정하지 않았다.

### 시뮬레이터의 한계

- 시점 간 자기상관 없음. 실제 KPI는 직전 값과 강하게 상관되지만
  각 시점을 독립 정규분포로 생성했다.
- KPI 간 물리적 결합 없음. 계절성을 공유해 간접적으로만 상관된다.
  실제로는 PRB 점유율 상승이 SINR 저하로 이어지는 등의 인과가 있다.

두 항목 모두 실제 데이터보다 탐지를 쉽게 만드는 방향으로 작용한다.

### 기타
