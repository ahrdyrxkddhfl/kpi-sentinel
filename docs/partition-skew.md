# 파티션 쏠림: 셀 8개가 파티션 4개에 고르게 나뉘지 않음

상태: 기록만 함 (아직 영향 없음, 조치 보류)
발견: 2026-09-29, 커밋 `1780b28` (셀 ID 키 기반 파티션 분산 전송) 검토 중

---

## 현상

`config/stream.yaml`의 `multi_entity` 설정(셀 8개, 파티션 4개, `murmur2_random`)으로
각 셀 키가 들어갈 파티션을 계산하면 다음과 같다.

| 파티션 | 셀 | 셀 수 | 데이터 비중 |
|---|---|---|---|
| p0 | (없음) | 0 | 0% |
| p1 | cell-003, cell-004, cell-007 | 3 | 37.5% |
| p2 | cell-000, cell-001, cell-002, cell-006 | 4 | 50% |
| p3 | cell-005 | 1 | 12.5% |

고르게 나뉘면 파티션마다 셀 2개(25%)가 들어가야 한다. 실제로는 p0이 비고
p2에 전체의 절반이 몰린다. 셀마다 행 수가 같으므로 셀 수 비율이 곧 데이터 비율이다.

확인 방법:

- 계산: Kafka Java 클라이언트의 murmur2를 Python으로 옮겨 계산했다.
  Kafka `UtilsTest`의 테스트 벡터 6개와 결과가 모두 일치했다.
  파티션 = `(murmur2(key) & 0x7fffffff) % 파티션 수`.
- 실측: `scripts/run_produce_cells.py`로 브로커에 241,920건을 실제로 보내 확인했다.
  파티션별 건수는 p0 0건, p1 90,720건, p2 120,960건, p3 30,240건으로 계산과 같았고,
  모든 셀이 하나의 파티션에만 들어갔다.

## 추정 원인

코드 결함이 아니라 **키 수가 너무 적어서** 생긴다.

해시 파티셔닝은 키마다 파티션을 사실상 무작위로 고르는 것과 같다.
키가 많으면 평균적으로 고르게 나뉘지만, 키가 8개면 공 8개를 상자 4개에
던지는 것과 같아서 우연히 치우치기 쉽다.

- 8개가 정확히 2개씩 나뉠 확률: 약 3.8% (2520 / 4⁸)
- 빈 파티션이 하나 이상 생길 확률: 약 38%

셀 수를 늘리면 쏠림이 빠르게 줄어든다. 파티션 4개 기준, 가장 많은 파티션의
셀 수를 평균으로 나눈 값은 다음과 같다(1.00이 완전 균등).

| 셀 수 | 파티션별 셀 수 | 최대 / 평균 |
|---|---|---|
| 8 | 0, 3, 4, 1 | 2.00 |
| 16 | 4, 3, 5, 4 | 1.25 |
| 32 | 9, 6, 9, 8 | 1.12 |
| 128 | 30, 36, 31, 31 | 1.12 |
| 1000 | 246, 263, 258, 233 | 1.05 |

## 문제점

- **순서 보장에는 영향 없다.** 한 셀은 항상 한 파티션에만 들어가므로
  셀 단위 순서는 지켜진다. `run_produce_cells.py`가 검증하는 것도 이 부분이다.
- **병렬 처리 효율이 떨어진다.** 컨슈머를 파티션 수만큼(4개) 띄워도
  p0 담당은 할 일이 없고, p2 담당이 전체의 절반을 혼자 처리한다.
  전체 처리 시간은 가장 바쁜 컨슈머가 결정하므로, 4배가 아니라 2배까지만 빨라진다.
- **현재 영향 범위:** `kpi-cells` 토픽을 읽는 컨슈머가 아직 없다.
  컨슈머 그룹으로 병렬 처리하는 실험을 시작할 때 문제가 드러난다.

## 개선 방안

| 방안 | 효과 | 대가 |
|---|---|---|
| A. 그대로 두고 기록 | 변경 없음 | 병렬 처리 실험의 처리량 수치가 쏠림 때문에 왜곡된다 |
| B. 셀 수 늘리기 (예: 32개 이상) | 쏠림이 약 1.1배 수준으로 줄어든다. 실제 통신망도 셀이 수백~수천 개라 현실에 가깝다 | 데이터 생성과 전송 시간이 늘어난다 |
| C. 파티션 수 조정 | 지금 셀 8개에서 파티션 2개면 4:4로 균등하다 | 우연히 맞춘 것이라 셀 구성이 바뀌면 다시 깨진다. 병렬도도 2로 줄어든다 |
| D. 파티션 직접 지정 (셀 번호 % 파티션 수) | 항상 완전 균등하다 | 프로듀서가 셀 번호 체계를 알아야 한다. murmur2를 고른 이유(다른 언어 프로듀서와 같은 배치)가 약해진다 |

키 이름을 바꿔서 해시가 고르게 나오게 맞추는 방법은 쓰지 않는다.
원인을 해결하는 게 아니라 결과만 맞추는 것이기 때문이다.

**권장:** 지금은 A로 두고, 컨슈머 그룹 병렬 처리 실험을 시작할 때 B를 적용한다.
적용 전후로 `run_produce_cells.py`의 파티션별 건수와 컨슈머별 처리 시간을
측정해 이 문서에 추가한다.
